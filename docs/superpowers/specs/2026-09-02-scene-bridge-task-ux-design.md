# 相邻片段路线打通任务交互修复设计

## 目标

修复项目片段管理页将轨迹反算与相邻路线打通混为同一状态的问题，让用户明确知道当前排队的是哪类任务、取消的是哪类任务，并允许关闭等待弹窗而不取消后台任务。

## 已确认根因

- 项目快照为每个片段同时保留 trajectory、render、scene_bridge，但顶层只选择一个 `job/status/progress` 展示。
- 前端取消按钮只依据顶层 `job_id`，按钮文案始终是“取消”，用户无法判断任务类型。
- 打通能力只把“尚无成功的预计算重叠 SfM”解释为“需重新轨迹反算”，没有区分目标片段已排队、正在运行或真正缺失结果。
- 路线打通等待弹窗没有关闭入口，轮询完成后无条件跳转目标工作台。
- scene_bridge 与 trajectory 同属 `heavy_compute` 且优先级相同，批量任务会让用户刚提交的交互任务排在剩余批次之后。

## 设计

1. 顶层任务继续保持兼容，但项目管理页根据 `job_type` 显示“轨迹反算排队中”“路线打通排队中”等明确状态，并把操作文案改为“取消反算”“取消打通”等任务相关文字。
2. 相邻片段能力检查识别目标片段的最新轨迹任务：排队时提示“目标片段轨迹反算已排队，完成后可打通”；运行/准备/校验时提示“目标片段轨迹反算中，完成后可打通”；只有没有当前成功结果且没有活动任务时才提示重新反算。
3. 向上和向下的不可用原因分别呈现，禁止再用 `up || down` 合并成一条无方向提示。
4. 等待弹窗增加关闭按钮并支持 Esc。关闭只隐藏弹窗，后台轮询与任务继续；任务成功时，弹窗仍打开才自动进入目标工作台，用户已关闭则只刷新状态并通知完成。
5. scene_bridge 使用高于普通批量轨迹任务的队列优先级，但仍使用 `heavy_compute`，不与当前 SfM 并发。当前重任务结束后先运行打通，再恢复剩余批量任务。

## 非目标

- 不修改 SfM、Pure Rotation、路线拟合和场景打通算法。
- 不取消或重跑已经成功的目标轨迹。
- 不改变后台任务的持久化与恢复契约。
- 不增加真正的重计算并行，避免 GPU/CPU/内存争用。

## 验证

- 后端单元测试覆盖活动目标轨迹的三种提示以及 scene_bridge 优先级。
- 静态前端测试覆盖任务类型文案、方向提示、弹窗关闭与关闭后不自动跳转。
- 运行项目/工作台聚焦测试、完整相关测试以及 `git diff --check`。

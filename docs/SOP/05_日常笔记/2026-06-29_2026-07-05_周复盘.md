# 周复盘：2026-06-29 至 2026-07-05

> 这份复盘承接上上周的原型链路，重点说明为什么要从 2D 追踪路线转向 SfM 3D 骨架路线。

## 0. 本周背景

上上周已经完成了场景二 `hygs` 的基础原型：可以选关键帧、做 visible-window 追踪、导出 Web Viewer 数据，也可以用短片段调试。

但问题也逐渐清楚：没有 SRT 的视频，如果只靠 2D 图像运动往后推，长距离很容易漂移。

这里的 2D 图像运动可以理解成“看画面里纹理怎么移动，再反推相机怎么动”。它在短片段里能用，但在长视频里会遇到两个问题：

1. 每一帧都依赖上一帧，误差会累积。
2. 局部看起来对，不代表整段道路位置都对。

所以本周的主线，是从旧的 2D/LK 外推路线，转向 SfM 3D 骨架路线。

SfM 是 Structure from Motion 的缩写，白话说就是：从视频或多张图片里，反推出相机的真实运动轨迹，以及场景的大致三维结构。

## 1. 本周总进度

本周主要完成了六件事：

1. 核查 Python 和 Web Viewer 的相机模型是否一致。
2. 把 visible-window 和多区域锚点问题测试化。
3. 建立运动先验，判断追踪结果是否符合视频运动趋势。
4. 抽象出 `video_path` 子包，把轨迹、锚点、道路中心线、诊断分模块管理。
5. 加入 CAD 约束评分和 refine，尝试用 CAD 反过来约束轨迹。
6. 跑通 SfM 对齐、质量评估、关键帧建议和 Web Viewer 3D 诊断场景。

## 2. 6 月 29 日：核查相机模型一致性

### 做了什么

新增：

- `cadvideo/pipeline/audit_camera_model_consistency.py`

对应产物：

- `out/hygs_camera_model_audit_2kf/camera_model_audit_report.md`

### 为什么要做

Python 端、Web Viewer 端、关键帧 JSON 文件都在描述“相机在哪里、朝向哪里、视野多大”。如果这些地方对相机参数的理解不一致，后面就会出现很难排查的问题。

例如：

- pitch 是向下为负，还是向下为正？
- yaw 的角度方向是否一致？
- Web 里的坐标是不是 CAD 原始坐标？
- 前端显示的相机和后端渲染的相机是不是同一个模型？

### 遇到的问题

如果相机模型不一致，表现可能不是明显报错，而是“总是差一点”。人工调很久也调不准，因为底层定义本来就不一致。

### 怎么解决

做相机模型审计，检查关键帧、前端、后端坐标和姿态约定是否一致。

### 阶段结论

继续优化算法前，必须先确认坐标系和相机模型没有内耗。

## 3. 6 月 30 日：把追踪问题测试化

### 做了什么

新增测试：

- `tests/test_visible_window_diagnostics.py`
- `tests/test_multi_region_anchor.py`

### 为什么要做

之前很多判断依赖肉眼看 overlay 视频：线稳不稳、窗口有没有跟上、关键帧有没有偏。这种方式不利于长期维护。

测试化的意义是：把“看起来不对”变成明确的诊断字段和自动检查。

### 遇到的问题

visible-window、多区域锚点、ROI 采样这些逻辑，如果没有测试，很容易在后续修改时被破坏。

### 怎么解决

增加测试，检查诊断字段、采样逻辑、锚点行为是否符合预期。

### 阶段结论

项目开始从“凭肉眼调算法”，转向“用指标和测试约束算法行为”。

- `tests/test_multi_region_sampling_diagnostics.py`
- `tests/test_organize_project_outputs.py`
- `tests/test_video_camera_path.py`

### 为什么要做

运动先验可以理解成：先从视频整体判断“无人机大概往哪个方向飞、速度是否稳定”，再用这个判断检查追踪结果。

如果追踪结果突然跳到一个不符合视频运动趋势的位置，就说明它可能错了。

`video_path` 子包则是为了工程化。之前很多逻辑混在 pipeline 脚本里，后续会越来越难维护。拆成子包后，道路中心线、锚点、运动模型、诊断、渲染都能独立测试。

### 遇到的问题

旧路线的逻辑越来越复杂，继续堆在单个脚本中，会导致：

- 修改风险高；
- 测试困难；
- 不同思路难以复用；
- 产物越来越难整理。

### 怎么解决

把视频路径相关能力抽象成 `cadvideo/video_path/` 子包，并补充测试。新增 `organize_project_outputs.py`，帮助整理大量实验产物。

### 阶段结论

项目从“原型脚本”进一步走向“模块化算法工程”。

## 5. 7 月 2 日：加入 CAD 约束，并启动 SfM 路线

### 做了什么

新增 CAD 约束与 refine 相关能力：

- `cadvideo/video_path/cad_score.py`
- `cadvideo/video_path/cad_refine.py`
- `cadvideo/pipeline/refine_video_camera_path_with_cad.py`

对应测试：

- `tests/test_video_path_road_score.py`
- `tests/test_video_path_cad_refine.py`

同时出现 SfM 相关产物：

- `out/hygs_sfm_align_0_250/`
- `out/hygs1min_sfm_align_full/`
- `out/hygs1min_sfm_refine_v2/`
- `out/hygs1min_sfm_align_v2/`

### 为什么要做

CAD 不只是被叠加的对象，也可以反过来作为约束。比如相机轨迹投影出来的 CAD 道路线，如果明显和视频道路边缘不一致，就说明相机轨迹可能偏了。

同时，本周开始明显转向 SfM。原因是旧路线只靠 2D 画面运动，不够稳定；SfM 能先从视频里恢复相机 3D 运动，作为更可靠的骨架。

### 遇到的问题

旧路线长视频漂移，本质原因是缺少全局运动骨架。每一帧只看局部图像，容易被局部纹理误导。

另一个问题是 semantic refine 尝试后效果变差。`out/hygs1min_sfm_refine_v2` 后来被标记为不推荐使用。

### 怎么解决

转向 SfM 3D 骨架：

1. 用 SfM 从视频中重建相机运动轨迹。
2. 用人工关键帧把 SfM 世界对齐到 CAD 世界。
3. 对关键帧之间做分段锚定，吸收 SfM 漂移。
4. 暂停使用效果变差的 semantic refine。

### 阶段结论

本周的路线判断发生了关键变化：场景二不能只靠 2D 传播，应以 SfM 3D 轨迹为主骨架。

### 为什么要做

以前算法输出一个 overlay 视频，人只能看“贴得好不好”。但如果不好，不容易知道：

- 哪一段风险最高；
- 是离关键帧太远，还是 SfM 自身质量差；
- 是轨迹漂移，还是 CAD 对齐有问题；
- 下一步应该补哪一帧关键帧。

质量评估模块就是为了解决这个问题。

### 产物说明

`quality_timeline.csv`：逐段记录质量和风险。

`quality_report.md`：汇总质量情况。

`keyframe_suggestions.json`：告诉用户建议在哪些帧补关键帧。

`camera_track_pred_quality.json`：带质量信息的预测轨迹。

`quality_diagnostics.png`：质量诊断图。

`sfm_viewer_scene.json`：给 Web Viewer 用的 SfM 3D 诊断场景。

### Web Viewer 新能力

Web Viewer 不再只是看视频叠加，还能看 3D 场景：

- SfM 点云；
- 原始 SfM 相机轨迹；
- CAD 锚定后的最终轨迹；
- 关键帧建议；
- 当前播放帧对应的相机位置。

这让用户能直观看到：原始 SfM 轨迹和最终锚定轨迹差在哪里，哪些位置可能需要补关键帧。

### 阶段结论

Web Viewer 从“手动调相机工具”升级为“诊断和闭环平台”。

## 7. 本周主要问题、原因和解决方式

### 问题 1：无 SRT 长视频容易漂移

表现：关键帧附近能对齐，但越远离关键帧越偏。

原因：没有 GPS/yaw 这种逐帧绝对定位，旧路线只靠局部图像运动外推。

解决：切到 SfM 3D 骨架，用视频本身恢复相机运动，再用关键帧锚定到 CAD。

下次检查：不要只看关键帧附近，要看关键帧之间、远离锚点处、转弯处和立交处。

### 问题 2：局部 ROI 看似对齐，整体可能错

表现：小窗口里线贴合，但完整 CAD 或远处道路不对。

原因：ROI 太窄，只看局部纹理；斜视场景下局部线段容易误匹配。

解决：引入质量评估、多区域采样、完整 CAD 诊断和关键帧建议。

下次检查：局部对齐后必须看完整 CAD、远近景分区和 quality timeline。

### 问题 3：semantic refine 结果变差

表现：`out/hygs1min_sfm_refine_v2` 全程漂移。

原因：基线已经较好，refine 空间很小；Chamfer 目标不稳定，修正量频繁顶到上限。

解决：当前不采用 semantic refine，推荐使用 `out/hygs1min_sfm_align_v2`。

下次检查：任何 refine 结果都必须和基线 overlay 对比，不能只看局部改善。

### 问题 4：产物太多，推荐版本不清楚

表现：`out/` 里有大量 `sfm_align`、`quality`、`refine`、`viewer_scene` 目录，容易拿错版本。

原因：实验推进快，但推荐版本和废弃版本没有及时写清。

解决：建立 SOP 和成果库，标明当前推荐演示组合。

下次检查：每次形成可演示版本，都记录输入、命令、输出目录、推荐状态和废弃状态。

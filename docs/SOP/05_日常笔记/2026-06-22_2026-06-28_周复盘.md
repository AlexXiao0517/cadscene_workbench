# 周复盘：2026-06-22 至 2026-06-28

> 面向 0 基础读者：这份复盘先解释项目背景，再按日期说明本周做了什么、为什么做、遇到什么问题、怎么解决。

## 0. 项目背景

这个项目要解决的问题，是把工程 CAD 图纸里的道路设计线，准确叠加到无人机航拍视频上。

可以把它理解成：视频里有一条真实道路，CAD 图纸里也有这条道路的设计线。我们希望 CAD 里的道路边线、中心线像“贴纸”一样，逐帧贴在视频里的真实道路上，而且不能随着无人机飞行越来越偏。

这个事情难在：

- CAD 是俯视平面图，视频是斜着拍的真实画面，视角不一样。
- 无人机视频每一帧都在动，CAD 线也要跟着每一帧变化。
- `hygs` 这个场景没有完整 SRT 遥测文件，也就是没有 GPS、高度、云台角度等逐帧定位信息。
- CAD 图纸里不只有道路，还有图层、标注、辅助线、圆弧、桩号线等复杂内容。

本周的核心目标，是把场景二 `hygs` 从“只能手动贴准一帧”，推进到“能沿视频传播、能在浏览器里查看、能人工补关键帧”的原型链路。

## 1. 本周总进度

这一周主要做了五件事：

1. 检查 CAD 道路线本身是否正确，尤其是弯道有没有被错误地变成直线。
2. 建立关键帧对齐能力，让某一帧可以先人工调准。
3. 尝试从这一帧向后追踪相机位置，验证整段视频叠加的可能性。
4. 引入 visible-window 逻辑，解决“相机脚下位置”和“画面看到的道路位置”不一致的问题。
5. 搭建 Web Viewer 数据和关键帧工作流，让人工复核、补帧、导出轨迹成为可能。

## 2. 6 月 22 日：检查 CAD 几何和首帧对齐

### 做了什么

这一天重点处理 CAD 曲线、关键帧对齐和早期相机追踪。

关键产物包括：

- `out/hygs_bulge_check/`
- `out/hygs_visual_refine_k44/`
- `out/hygs_camera_track_groundplane_10s/`

### 为什么要做

后续所有叠加都依赖 CAD 道路线。如果 CAD 线本身是错的，比如真实弯道被程序读成直线，那么后面无论怎么投影、怎么追踪，都会把错误的线贴到视频上。

这里的一个关键概念是 `bulge`。在 CAD 的 LWPOLYLINE 里，圆弧有时不是直接存成很多点，而是用一个叫 bulge 的参数表示。如果程序只读取起点和终点，不展开 bulge，弯道就会变成一条直线。

### 遇到的问题

`hygs` 的道路中心线和边线包含圆弧，但早期提取时可能只按折线顶点处理。这会导致：

- CAD 预览里道路弯曲形态不够准确；
- 视频叠加时弯道看起来像折线；
- 后续追踪和评分都基于错误几何。

### 怎么解决

先做 `hygs_bulge_check` 检查，对比 bulge 展开前后的效果，确认问题存在。后续需要在 CAD 解析层把 bulge 展开为足够密的采样点，再导出 road JSON。

同时做了关键帧视觉微调。也就是先选一帧，把 CAD 线大致投影到视频上，再用图像边缘做小范围自动修正。

### 阶段结论

首帧能够对上，但“后续帧怎么稳定跟上”还没有完全解决。CAD 几何正确性也被确认是必须优先处理的基础问题。

## 3. 6 月 23 日：引入 visible-window

### 做了什么

这一天推进了 visible-window 路线，关键产物集中在：

- `out/hygs_camera_track_visible_20s/camera_poses.json`
- `out/hygs_camera_track_visible_20s/camera_poses.csv`
- `out/hygs_camera_track_visible_20s/track_visible_window_report.md`
- 多个 overlay 叠加视频

### 为什么要做

旧逻辑大致是：根据相机在地面上的投影点，也就是 `camera_s`，决定当前应该取 CAD 的哪一段来匹配。

但在无人机斜着向前拍的时候，这个逻辑会出问题。相机脚下可能还在道路起点附近，但画面里其实已经看到更前方的道路。如果继续用脚下位置裁 CAD，就会拿偏后的 CAD 路段去匹配当前画面。

### 遇到的问题

典型现象是：画面里的道路已经向前推进，但 CAD 匹配窗口还停在后面，导致叠加线和真实道路逐渐不同步。

### 怎么解决

引入 visible-window。白话说，就是不再问“无人机脚下在哪里”，而是问“当前画面实际能看到哪段路”。

具体做法是：

1. 根据虚拟相机参数估计当前画面视野。
2. 把这个视野反投影到地面。
3. 判断地面范围对应 CAD 中心线的哪一段里程。
4. 用这段可见里程范围裁剪 CAD，作为当前匹配窗口。

### 阶段结论

系统开始区分两个概念：

- 无人机在哪里；
- 画面里看到哪段路。

这个区分非常关键，因为它解决了斜视前飞时 CAD 窗口滞后的问题。

## 4. 6 月 24 日：补 CAD 预览和 Web Viewer 基础

### 做了什么

新增或更新了：

- `scripts/preview_cad_json.py`
- `scripts/cad_to_json.py`
- `scripts/render_cad_projection.py`
- `web_camera_viewer/vendor/three.min.js`
- `web_camera_viewer/vendor/controls/OrbitControls*.js`
- `web_camera_viewer/vendor/controls/TransformControls.global.js`

### 为什么要做

算法项目里，很多问题不是“没有算法”，而是“看不清算法错在哪里”。所以需要可视化工具：

- 看 CAD JSON 是否导出正确；
- 看 CAD 线投影到画面的位置；
- 看相机在 3D 空间里的位置和朝向；
- 看轨迹是否跳变。

### 遇到的问题

纯 Python 脚本输出一堆 JSON、CSV 和视频，调试不直观。特别是无 SRT 场景，很多时候要靠人工判断哪一帧对齐、哪一段漂移，只有命令行产物不够。

### 怎么解决

开始搭建 Web Viewer 基础。Web Viewer 后续承担两个角色：

1. 查看器：播放视频，同时叠加 CAD 线。
2. 编辑器：人工调整相机、添加关键帧、导入导出轨迹。

### 阶段结论

调试方式从“只看脚本输出”，开始转向“浏览器里可视化检查”。

## 5. 6 月 25 日：形成 Web Viewer 与关键帧工作流

### 做了什么

关键产物包括：

- `data/hygs/`
- `data/hygs_1min/`
- `tmp_cadvideo/next_segment_smoke/`
- `tmp_cadvideo/next_segment_1min_smoke/`
- `cadvideo/pipeline/track_next_segment.py`
- `cadvideo/pipeline/merge_review_keyframe.py`

### 为什么要做

场景二没有 SRT，单靠算法从头追到尾容易漂移。因此需要“关键帧”。

关键帧可以理解为人工确认过的锚点。例如第 270 帧、500 帧、750 帧分别调准一次，算法就可以在这些锚点之间插值或重新对齐，减少漂移。

### 遇到的问题

如果每次追踪失败都要重新跑完整流程，效率会很低。还需要一个方式，把人工复核后的关键帧重新合并到轨迹里。

### 怎么解决

形成“追踪 -> 人工复核 -> 合并关键帧”的流程：

1. `track_next_segment.py` 负责从已有关键帧继续追踪下一段。
2. Web Viewer 或人工检查负责确认某些帧是否需要调整。
3. `merge_review_keyframe.py` 把确认后的关键帧合并回轨迹。

同时导出 `hygs_1min` 短片段，用 1 分钟视频替代完整大视频调试。这样加载更快、跳帧更稳定，也更适合演示。

### 阶段结论

项目从“一次性跑算法看结果”，进入“算法与人工复核协作”的阶段。

## 6. 6 月 26 日：打通 Web 和 Python 数据格式

### 做了什么

新增或更新：

- `data/hygs/design.json`
- `data/hygs/camera_track.json`
- `data/hygs_1min/design.json`
- `data/hygs_1min/hygs_1min.mp4`
- `scripts/render_static_track_preview.py`
- `cadvideo/pipeline/convert_web_camera_track.py`

### 为什么要做

Web Viewer 和 Python pipeline 必须能互相读懂数据。

前端负责人工查看、调相机、导出关键帧；Python 负责计算、追踪、对齐、渲染。如果两边格式不通，前端调好的结果就不能进入后端流程。

### 遇到的问题

不同模块对相机轨迹、CAD 坐标、视频帧号的表示方式不完全一样，容易出现：

- 帧号对不上；
- 坐标系不一致；
- 前端导出的轨迹不能直接给 Python 用；
- Python 产物不能直接在浏览器里加载。

### 怎么解决

通过 `design.json`、`camera_track.json` 和轨迹转换工具，把 CAD、视频、相机轨迹统一成 Web Viewer 能加载、Python 也能继续处理的格式。

### 阶段结论

Web Viewer 不再只是展示页面，而成为算法流程里的一个正式编辑节点。

## 7. 本周问题总结

### 问题 1：CAD 弯道可能被读成直线

原因：LWPOLYLINE 的 bulge 圆弧没有正确展开。

解决：先做检查报告确认问题，后续应在 CAD 解析层展开 bulge。

下次检查：导出道路 JSON 前，必须抽查弯道路段的 CAD 原图、JSON 预览和 overlay 是否一致。

### 问题 2：相机脚下位置不能代表画面可见道路

原因：斜视前飞时，画面看到的是前方道路，不是相机脚下那一点。

解决：使用 visible-window，根据画面可见范围裁剪 CAD。

下次检查：日志里同时看 `camera_s`、`visible_s_center`、`match_window`。

### 问题 3：单帧对齐不等于整段稳定

原因：无 SRT 场景缺少逐帧绝对定位，靠局部图像运动传播会积累误差。

解决：引入关键帧、下一段追踪、人工复核和合并流程。

下次检查：不要只看关键帧附近，必须看关键帧之间和远离关键帧的位置。
